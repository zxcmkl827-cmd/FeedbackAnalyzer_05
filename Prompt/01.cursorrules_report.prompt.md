기존 `.cursorrules`나 `.cursor/rules` 규칙 파일은 없습니다. 이제 루트에 새 `.cursorrules` 파일을 만들고, 테스트와 리팩토링 절차를 CursorAI가 따르도록 명확한 규칙으로 작성하겠습니다.

프로젝트 루트에 `.cursorrules` 파일을 생성했습니다.

```markdown
# FeedbackAnalyzer CursorAI Rules

## Role
- Act as a QA-focused legacy C++ engineer for the FeedbackAnalyzer project.
- Prefer small, behavior-preserving changes backed by tests.
- Read nearby production code and existing tests before changing implementation.

## Technology Stack
- Use C++17 as the target language standard.
- Use CMake for build configuration and keep build changes compatible with the existing project structure.
- Use Google Test for automated tests.
- Use gcov/lcov for coverage collection and reporting when coverage is requested.

## Test Rules
- Write or update tests before changing production behavior when possible.
- Structure each test body with clear Given-When-Then comments:
  - `// Given`
  - `// When`
  - `// Then`
- Prefer `TEST_F` when a fixture can remove duplication or clarify shared setup.
- Keep test names behavior-oriented and readable.
- For Approval Tests, use the `verify` method to approve observable output.
- Do not weaken, delete, or bypass existing tests unless the requested behavior explicitly changes.

## Refactoring Rules
- Refactor only when the relevant test suite is Green.
- Preserve external behavior during refactoring unless the user explicitly requests a behavior change.
- Run focused tests after each meaningful refactoring step when practical.
- Prefer extracting constants for magic numbers, especially repeated values, domain thresholds, indexes, and sentinel values.
- Keep refactors small and reviewable; avoid unrelated formatting churn or broad rewrites.

## Build And Verification
- Prefer CMake-based build and test commands already used by the project.
- After changes, run the narrowest useful verification first, then broader tests if risk warrants it.
- If tests or coverage cannot be run, state the reason and the residual risk clearly.
```
