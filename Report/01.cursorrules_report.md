# FeedbackAnalyzer `.cursorrules` 작성 보고서

## 1. 작업 개요

FeedbackAnalyzer 프로젝트에서 CursorAI가 레거시 C++ 코드 QA 엔지니어 관점으로 일관되게 동작하도록 프로젝트 루트 경로에 `.cursorrules` 파일을 작성했다.

초기 요청에서는 C++17, CMake, Google Test, lcov/gcov 기반의 기술 스택과 테스트 및 리팩토링 규칙을 포함한 CursorAI 규칙 파일 생성을 요구했다. 이후 영어로 작성된 규칙 문구를 한글로 재작성하는 요청에 따라 최종 `.cursorrules` 파일을 한국어 기준으로 수정했다.

## 2. 반영 요구사항

- 기술 스택은 C++17, CMake, Google Test, gcov/lcov를 기준으로 명시했다.
- 테스트 규칙에는 Given-When-Then 주석 구조를 포함했다.
- Google Test 작성 시 필요한 경우 `TEST_F` 사용을 우선하도록 작성했다.
- Approval Test 작성 시 `verify` 메소드를 사용하도록 명시했다.
- 리팩토링은 관련 테스트가 Green 상태일 때만 진행하도록 제한했다.
- 매직 넘버는 상수로 추출하는 것을 권장하도록 작성했다.
- 영어로 작성된 설명 문구는 한국어로 재작성하되, `C++17`, `CMake`, `Google Test`, `gcov/lcov`, `TEST_F`, `verify`, `Given-When-Then` 같은 기술 키워드는 그대로 유지했다.

## 4. 최종 `.cursorrules` 내용

```markdown
# FeedbackAnalyzer CursorAI 규칙

## 역할
- FeedbackAnalyzer 프로젝트의 레거시 C++ 코드 QA 엔지니어로 행동한다.
- 테스트로 뒷받침되는 작고 동작 보존적인 변경을 우선한다.
- 구현을 변경하기 전에 주변 운영 코드와 기존 테스트를 먼저 읽는다.

## 기술 스택
- 대상 언어 표준은 C++17을 사용한다.
- 빌드 구성은 CMake를 사용하며, 기존 프로젝트 구조와 호환되도록 유지한다.
- 자동화 테스트는 Google Test를 사용한다.
- 커버리지 수집과 리포트가 필요한 경우 gcov/lcov를 사용한다.

## 테스트 규칙
- 가능하면 운영 코드의 동작을 변경하기 전에 테스트를 먼저 작성하거나 갱신한다.
- 각 테스트 본문은 명확한 Given-When-Then 주석 구조로 작성한다.
  - `// Given`
  - `// When`
  - `// Then`
- 픽스처가 중복을 줄이거나 공통 준비 과정을 명확히 할 수 있으면 `TEST_F`를 우선 사용한다.
- 테스트 이름은 동작 중심으로 읽기 쉽게 작성한다.
- Approval Test를 작성할 때는 관찰 가능한 출력 검증에 `verify` 메소드를 사용한다.
- 요청된 동작이 명시적으로 변경되지 않는 한 기존 테스트를 약화, 삭제, 우회하지 않는다.

## 리팩토링 규칙
- 관련 테스트 스위트가 Green 상태일 때만 리팩토링한다.
- 사용자가 동작 변경을 명시적으로 요청하지 않는 한 리팩토링 중 외부 동작을 보존한다.
- 가능하면 의미 있는 리팩토링 단계마다 관련 테스트를 실행한다.
- 매직 넘버는 상수 추출을 권장하며, 특히 반복 값, 도메인 임계값, 인덱스, 센티널 값에 적용한다.
- 리팩토링은 작고 리뷰 가능한 단위로 유지하며, 관련 없는 포맷 변경이나 광범위한 재작성을 피한다.

## 빌드 및 검증
- 프로젝트에서 이미 사용하는 CMake 기반 빌드 및 테스트 명령을 우선한다.
- 변경 후에는 가장 좁고 유용한 검증을 먼저 실행하고, 위험도가 높으면 더 넓은 테스트를 실행한다.
- 테스트나 커버리지를 실행할 수 없다면 그 이유와 남은 위험을 명확히 설명한다.
```

## 5. 확인 결과

`.cursorrules` 파일은 프로젝트 루트에 생성되었고, 영어 설명 문구는 한국어로 재작성되었다. 요청된 테스트 규칙, 리팩토링 규칙, 기술 스택 항목이 모두 포함되어 있다.
